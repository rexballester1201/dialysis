Dialysis Centre Management System

Deploying to cPanel, with no shell

For one haemodialysis unit on shared hosting, where the only tools are cPanel, File Manager and phpMyAdmin. Work top to bottom — step 0 can end the deployment, so do it first. The full reasoning behind every step is in deploy/DEPLOYMENT.md.

  • You need: cPanel with MySQL 8.0.16+, PHP 8.2+
  • On your own computer: PHP 8.1+ and Node, for steps 8 and 10
  • This page holds no passwords
0 of 13 steps done
  1. 0

    Confirm the database server is MySQL, not MariaDB

    Open phpMyAdmin and run:

    SELECT VERSION();
    • MySQL 8.0.16 or newer — continue. A suffix such as 8.4.9-cll-lve is CloudLinux's MySQL and is fine.
    • Older MySQL — stop and ask the host to move you to a newer server. Before 8.0.16, MySQL silently ignores CHECK constraints.

    Anything saying MariaDB is a full stop. The quality view uses LEFT JOIN LATERAL, which MariaDB has never supported, so the schema will not import. Rewriting it is a project, not a deployment step — ask the host for MySQL first.

  2. 1

    Create the database and its user

    1. cPanel → MySQL Databases → create a database, e.g. dialysis (it becomes cpuser_dialysis).
    2. Create a user with a long random password.
    3. Add the user to the database with ALL PRIVILEGES.

    The import creates triggers and views. A user without those privileges imports the tables and silently skips the six triggers — the database-level safety backstops — while everything appears to work.

  3. 2

    Upload the application

    Upload the contents of apps/api/ to a folder outside the public web root, for example /home/cpuser/dialysis-api/. Include vendor/ (about 135 MB): upload it as one .zip and extract it in File Manager.

    Do not upload tests/, verify/, your local .env, storage/framework/testing/, or anything from deploy/.

    Point the domain at public/. Preferred: cPanel → Domains → set the document root to /home/cpuser/dialysis-api/public. If your plan cannot, copy public/ into public_html/ and change the two paths in its index.php:

    require __DIR__.'/../dialysis-api/vendor/autoload.php';
$app = require_once __DIR__.'/../dialysis-api/bootstrap/app.php';

    Keep public/.htaccess — without it every URL except / returns 404.

  4. 3

    Make the storage folders writable

    In File Manager, set these to 0755 (some hosts need 0775):

    storage/framework/sessions
storage/framework/cache
storage/framework/views
storage/logs
bootstrap/cache

    Sessions, cache and compiled views all live on disk; the application cannot boot without them.

  5. 4

    Import the database

    phpMyAdmin → select your database → Import. Import these from deploy/sql/, in this order, waiting for each to finish:

    1. 01-schema.sql — the schema: tables, views, triggers, constraints
    2. 02-post-baseline.sql — the sign-in token table and the later schema fixes
    3. 03-seed.sql — reference data: roles, shifts, chairs, drugs, the facility, one water system

    Then confirm it in the SQL tab:

    SELECT
  (SELECT COUNT(*) FROM information_schema.tables
     WHERE table_schema = DATABASE() AND table_type = 'BASE TABLE') AS tables_,
  (SELECT COUNT(*) FROM information_schema.views
     WHERE table_schema = DATABASE())                               AS views_,
  (SELECT COUNT(*) FROM information_schema.triggers
     WHERE trigger_schema = DATABASE())                             AS triggers_;

    Expect 69 tables, 12 views, 6 triggers. Zero triggers means the user lacked privileges (step 1).

    02, 03 and 04 are safe to import again — each adds only what is missing. Re-importing 01 stops at its first statement and changes nothing.

  6. 5

    Configure .env

    1. Copy deploy/.env.production.example to the application folder as .env.
    2. Fill in DB_DATABASE, DB_USERNAME and DB_PASSWORD — both names carry the cPanel prefix.
    3. Set APP_URL to your real https:// address.
    4. Generate APP_KEY: edit deploy/generate-key.php and set SECRET to a random string of 20+ characters, upload it beside index.php, visit https://your-domain/generate-key.php?key=YOUR-SECRET, paste the value (with base64:) into APP_KEY — then delete generate-key.php.

    Leave APP_DEBUG=false. With it on, any error page shows the configuration — database password included — to whoever triggered it.

  7. 6

    Run the pre-flight check

    Edit deploy/preflight.php, set SECRET to a random string of 20+ characters, upload it beside index.php, and visit https://your-domain/preflight.php?key=YOUR-SECRET.

    • Resolve every FAIL. The two about administrators and sign-in fail until step 8.
    • If bcmath is missing, enable it in cPanel → Select PHP Version → Extensions. It runs every money calculation.
    • Read the Unit timezone line against the wall clock. The unit's day is counted in that zone: which day a water check clears, the date the board opens on, when stock expires.

    Delete preflight.php when you are done with it (after step 8's re-run).

  8. 7

    Check the application answers

    https://your-domain/api/v1/health

    Expect JSON with database: ok and the table counts. redis: not_configured is correct — Redis is not used.

    A 404 here while / works means mod_rewrite or public/.htaccess is missing. A 500 means: read storage/logs/laravel.log in File Manager.

  9. 8

    Create the staff accounts

    There is no screen that creates staff or sets passwords, so accounts go in as SQL, written on your own computer by deploy/accounts/make-accounts.php.

    1. Put real names on the accounts. Open deploy/accounts/accounts.csv and replace each placeholder with the person who will hold it (PRC licence numbers where they apply). One account per person: the name on it is the name on every record it signs. Then generate the SQL and the credentials sheets: 
      php deploy/accounts/make-accounts.php
      To regenerate, add --force — only while nothing has been imported anywhere, because it prints new passwords.
    2. Import deploy/sql/04-accounts.sql in phpMyAdmin, like step 4.
    3. Hand out the sign-in details. Print deploy/accounts/CREDENTIALS.html — one slip per person — give each person only theirs, then delete it and CREDENTIALS.txt.
    4. Re-run the pre-flight: Administrator exists and Staff who can sign in now pass.

    The credentials files never go to the server, into email, or into a shared folder. The pre-flight fails if it finds one there.

    Later, on the same computer:

    # someone new: add their row to accounts.csv, then
php deploy/accounts/make-accounts.php RN-002

# a forgotten password (new password, lockout cleared, signed out everywhere)
php deploy/accounts/make-accounts.php --reset RN-001

    Nobody can change their own password in the app yet, so a reset is an administrator importing the reset file it writes.

  10. 9

    Schedule the background work

    cPanel → Cron Jobs → add one job running every minute (adjust the PHP path to what the Cron page shows, often /usr/local/bin/ea-php84):

    cd /home/cpuser/dialysis-api && /usr/local/bin/php artisan schedule:run >> /dev/null 2>&1

    It runs the controls check at 06:00 and 18:00 UTC (14:00 and 02:00 in Manila) and rebuilds the quality report at 02:30 UTC. The schedule runs on the server's UTC clock, not the unit's, so until that changes someone opens the Controls screen each morning before the first patient. Send cron failures to an email address someone reads.

    The controls check is what finds a cohort breach, a water exception or a failed dialyzer that got in some other way. A control nobody reads is not a control.

  11. 10

    Build and upload the two clients

    On a computer with Node, from the project folder:

    npm install
npm run build -w @dialysis/bedside
npm run build -w @dialysis/console

    Upload apps/bedside/dist/ to /bedside and apps/console/dist/ to /console on the same domain as the API (there is no cross-origin setup). Give each folder this .htaccess, with its own RewriteBase:

    <IfModule mod_rewrite.c>
  RewriteEngine On
  RewriteBase /bedside/
  RewriteCond %{REQUEST_FILENAME} !-f
  RewriteCond %{REQUEST_FILENAME} !-d
  RewriteRule . index.html [L]
</IfModule>

    Serve everything over HTTPS: both clients keep their sign-in token in the browser, and the bedside app's offline features need a secure origin.

  12. 11

    Configure the unit in Settings — before any patient

    Sign in to the console as the administrator and open Settings. Every setting explains its own consequence; these must be right first:

    • Chairs and infection control. Check every chair's cohorts against the real room. A chair with no cohort ticked is unrestricted, not unusable.
    • High-alert drugs. A flagged drug needs a witness who is not the giver. Match the list to your policy.
    • Benefit programme. The seed carries ₱6,350 per session and 156 sessions a year — verify both against the current PhilHealth circular. Both have changed before. Settings shows the programmes but cannot add one yet; a new rate is an API call, set out in the administrator's guide (docs/admin-guide.html).
    • Facility timezone. Where the unit actually is. It decides when the unit's day starts, so it decides whether the morning's first treatment may start.

    The seed's water system is called RO Unit A; rename it in the database to match yours.

  13. 12

    Prove it works, then go live

    Work through the final checklist below against the live installation. Every line is something that has gone wrong somewhere, quietly.

Final checklist

Against the live installation, before the first real patient.

Say these out loud before go-live

Known limitations of this build on shared hosting
  • No staff management in the app. Accounts, passwords and PINs exist only through the SQL that make-accounts.php writes; nobody can change their own password.
  • No queue worker and no Redis. Queue, cache and sessions run in-process and on disk — honest for one unit, and it stops being true the moment someone adds a background job.
  • The bedside app shell is not cached for offline start. Charting keeps working offline once the app is open, but opening it cold with no network shows nothing.
  • No automated UI tests, and CI has never run. Both clients were checked by hand; a regression will be found by a person.
  • Some setup needs the database: shifts, machines, adding a chair, and renaming the water system.
  • The scheduled check runs on UTC — 14:00 and 02:00 in Manila, not before the morning shift. Open the Controls screen each morning.
  • One failed chlorine test keeps the check red for 90 days — the water list keeps every breach of the last 90 days, corrected or not. Look for new rows, not a zero.
  • The Controls screen dates a water breach by the UTC day — a 05:30 Manila breach is listed under the day before. The check that blocks treatment uses the unit's own day.
  • CloudLinux limits apply. The nightly quality rebuild is the job most likely to hit them as years of sessions accumulate; check LVE faults if the quality report goes stale.
  • Backups are yours. These records are kept 10–15 years; cPanel's nightly overwrite is not a plan.
